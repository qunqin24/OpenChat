# 内容审核

> 规则摘要见 [AGENTS.md](../../AGENTS.md)；本文是完整设计说明。文中「后端约定」「前端约定」等指 AGENTS.md 的章节，细节按主题分在本目录各文件，索引见 [README.md](README.md)。

用户发的一切都以运营者的上游账号（OpenAI、Anthropic、中转站）名义发出，违规内容会让这些账号被封。所以：用户新发的输入先审核再发给模型，拒绝的记日志，反复违规的账号被停用；上游请求再带一个用户标识，万一被封也能定位到人。代码在 `internal/api/moderation*.go`、`end_user.go`，查询在 `queries/moderation.sql`。

## 检查什么、在哪儿

- 只检查**用户新发的输入**（外加用户自己写下、会进系统提示词的自定义指令和记忆，见下「自己写下的文字」）：发送（`CreateMessage`）的文字和图片附件、改写（`EditMessage`）的新文字（附件是第一次发送时审过的）、回答 `ask_user` 时用户**打的字**（`other`，选的选项是模型自己写的，不审）。
- 另外三处也审（来源见「日志与处罚」）：定时任务的指令，页面上保存时审（`task`，算违规），运行前哈希对不上或由模型写入时审（`task_run`，不算违规），见 [scheduled-tasks.md](scheduled-tasks.md#审核)；写作块里用户写的版本，等模型要读它时才审（`document`，算违规），见 [writing-blocks.md](writing-blocks.md#审核)。
- 消息引用了其他对话时，被引用对话的**标题**和这条消息一起送审（`withReferenceTitles`，`api/references.go`）：标题是用户随手改的、改名时不审，而模型会读到它；对话正文不再审。见 [conversations.md](conversations.md#引用其他对话)。
- **不审**：重新生成（重发的是审过的输入）、工具结果、网页内容、历史对话、标题、摘要——都不是用户新发的。新增会把用户输入送上游的路径要想清楚属于哪一类。
- 位置和容量检查一样：`chooseRun` 之后、事务之前，所以被拒绝的请求不建 run、不认领附件。拒绝是 **422 `content_blocked`**，`details.categories` 只列命中的类别名，不给分数、不给原文；服务不可用并且要拦时是 **503 `moderation_unavailable`**。幂等重试（`requestId` 已有 run）在检查之前就返回了，不会被重复审。

## 设置

全部在 `app_settings`，每个请求读一次（一条 `GetSettings` 查询），改了立即生效，保存时服务端校验（400 `invalid_moderation_*`、`moderation_key_required`、`moderation_model_required`），任何一项不合法就一项都不存；入口是 `GET/PATCH /admin/moderation`，页面在 后台 → 系统 →「审核」。
- **保存是一个事务**（`UpdateModerationSettings`）：先拿 `LockModerationSettings`（advisory lock，另有进程内的互斥，免得等锁的保存把连接池占满），在锁下读出现有设置、套上这次的改动、校验、10 个键一起写；中途失败整个回滚，旧设置原样（不会留下"模式是 model 却没有模型、`on_error` 是 allow"这类半截状态），两个同时的保存一个接一个套用而不是各自从旧值出发互相覆盖，读设置的一条 `GetSettings` 查询只会看到保存前或保存后的整套。存储里有读不出的值时，保存从默认值起（让运营者能改回来）。
- **读不全就拦**：`loadModeration` 读完所有行、把读得出的都返回，再把所有坏值作为错误一起报，`modeRead` 说明模式本身读没读出来。设置读不全时（有坏值、查询失败），`moderated` 返回 503 `moderation_unavailable`，**不看 `on_error`、不用默认值顶替**（可能正是 `on_error=block` 读不出来），**唯一的例外是模式读出来了、是 `off`**——没在审核，别的设置坏了无所谓。

- `moderation_mode`：`off`（默认）/ `openai` / `model`。
- `openai`：`moderation_openai_key`（只写不读，接口只报 `openaiKeySet` 和末 4 位，不进日志，错误信息里也抹掉）、`moderation_openai_base_url`（空 = `https://api.openai.com/v1`）。POST `{base}/moderations`，模型 `omni-moderation-latest`，输入是文字 + 图片（`image_url` data URL，最多 6 张、合计 24 MiB，超了是「太大」，见下），每个请求超时 5 秒。**整段文字都审，不取头尾**（聊天请求带的是全文，漏掉的中间就是藏东西的地方）：文字按 12000 字切成片（`splitForModeration`，相邻片重叠 400 字、切口尽量落在空白处，只有空白的片丢掉），片作为纯字符串数组发，一个请求最多 16 片，端点每片回一个 result，**少于片数就算检查失败**；图片和第一片放进同一个多模态请求。多个 result 按"任一标记、取高分"合并，已有类别命中就不再发剩下的请求。**绝对上限 400000 字**（`moderationMaxRunes`）：更长的文字不审一半放过，而是在任何模式下都 **413 `message_too_large_for_moderation`**（见下「太大不是故障」），不看 `on_error`；被设为豁免的管理员不审，不受此限。
- `model`：`moderation_model`，目录里的模型。按**服务端任务**走 `pickChannel`（`staff=true`，管理员发的请求带 `admin` 以便容量豁免，和 `taskModel` 一样），用量记新类型 `moderation`（`usage_logs_kind` 约束已加，所以花费上限会计入）。提示词是英文、模型可见（`moderationPrompt`），用户文字放在 `<message>` 标签里当不可信数据，里面的同名标签被转义成 `&lt;`；要求只回一个 JSON（`categories` 布尔 + `scores`），容忍代码围栏和前后文字，读不出来就算失败。**整段文字都审**：按 24000 字切片（同样重叠），逐片各发一次请求（各记一条 `moderation` 用量），任一片命中即拦、不再问剩下的；需要超过 8 次请求（约 19 万字）的文字**不审**，同样是 413 `message_too_large_for_moderation`，不看 `on_error`；分类模型的上下文装不下一片（`llm.ErrorContextLength`）也算「太大」，不是服务故障。**只审文字**，图片不给任意模型。`errModelCapacity`（模型满了）按"服务不可用"处理，不去问。
- **判定必须完整**（`verdictFrom`）：服务的回答要对**每个选中的拦截类别**给出布尔（模型模式是明确的 true/false，OpenAI 的 result 要有 `categories` 对象；`moderation_min_score` 大于 0 时还要有这些类别的分数），缺了、为 null、不是布尔、整个 `categories` 缺失（`{"categories":{}}`、只有分数没有布尔）都是**回答不可用**，走"服务出错"的 `on_error` 路径，**绝不当作"没问题"**。不认识的类别名和 0..1 之外的分数忽略。
- **太大不是故障**（`errMessageTooLarge`、`errTooLargeToCheck`）：消息的大小由发送者决定，所以「太大而无法完整检查」绝不能当成「服务出错」——`on_error=allow` 会放行后者，那样把文字垫长就能绕过审核（曾经的漏洞：被拒的文字垫到 20 万字后以 202 通过，一次分类请求都没发）。凡因大小而不能完整检查的，在任何模式、任何 `on_error`，都是 **413 `message_too_large_for_moderation`**，不写任何行、不记 strike、不算违规：文字超过绝对上限、模型模式超过 8 片、OpenAI 模式超过 6 张图片或图片合计超过 24 MiB、读图时发现文件比准入时大了（`storage.ErrTooLarge`，S3 预签名 PUT 可以在准入后再写一遍）、分类模型的上下文装不下一片。实现上这些都在检查代码里包一层 `errTooLargeToCheck`，`moderated` 的 `checkFailed` 见到它就返回 413，其余才走 `moderationFailed`（`on_error`）；模型模式的片数在 `pickChannel` 之前就数，所以不会先问一半。新增任何「因为输入太大而检查不了」的分支都要这样包，别返回裸 `error`。前端 `useSendError` 弹「这条消息太大，内容审核无法完整检查」，文字和文件原样留着（新对话的第一条消息也是：什么都没写，`startWroteNothing`）。已知剩余：模型模式下发送者可以用提示注入让分类模型答出读不了的回答，这属于「回答不可用」，仍按 `on_error`；服务商自己的内容过滤拒绝这段提示（HTTP 4xx）也读作服务出错。
- `moderation_categories`：拦截的类别，OpenAI 的 13 个类别里多选，默认 `sexual/minors`、`harassment/threatening`、`hate/threatening`、`illicit/violent`、`self-harm/instructions`、`violence/graphic`。`moderation_min_score`（默认 0）：为 0 只看接口给的布尔；大于 0 时，选中类别的分数达到它也算命中——**只会更严，不会放过布尔已标记的**。
- `moderation_exempt_admins`（默认**关**：管理员的消息发往同一个上游，同样要审）。
- `moderation_on_error`：`allow`（默认）/ `block`，服务**真的**出错（网络、5xx、超时、没渠道、模型满了、读不出的回答）时用户的消息怎么办；**消息本身太大不归它管**（见上）。
- `moderation_strikes`（默认 3，0 = 只记录不处罚）、`moderation_strike_window_hours`（默认 24）。

## 日志与处罚

- `moderation_events`（迁移 `…_content_moderation.sql`）：只记被拒绝的，不记通过的。`user_id`（`SET NULL`）、`conversation_id`（`SET NULL`）、`source`（`send|edit|answer|instructions|memory|snapshot|task|task_run|document`，`instructions`/`memory`/`snapshot` 见「自己写下的文字」，`task`/`task_run`/`document` 见上「检查什么、在哪儿」；当前的 CHECK 约束在迁移 `20261028014955_remove_guest_mode.sql`）、`mode`、`categories`、`excerpt`（原文前 500 字，运营者自己的记录，只有管理员能读）、`action`（目前只有 `blocked`）、`sanction`（这条事件触发了处罚才有：`disabled`）。90 天后由清理循环的 `purgeModeration` 删。**不要给这张表加"user_id 必须非空"的约束**：用户行删除时外键置空会撞上它。
- 接口（都在管理员分组，非管理员 404）：`GET /admin/moderation/events`（游标分页 `(created_at, id)`，过滤 `userId`、`category`，游标只对发出它的那组过滤有效）。
- 处罚在 `recordBlocked`：**一个事务**里按主体（`user:<id>`）取 advisory lock、写事件、数窗口内的违规、够了就处罚，所以并发的违规请求不会各数少一条。处罚只有停用账号：和管理员停用一样走 `AdminUpdateUser` 的 `disabled`，原因记为 `moderation`，**会话不删**，已开着的页面下次请求得到 403 `account_disabled` 并跳到停用页，说明窗口内被拦了几条、涉及哪些类别（见认证文档）；**管理员永远不自动停用，只记录**——这一条靠锁保证：够次数要处罚账号时，先在同一个事务里拿 `LockAdminMembership`（`UpdateUser`、`BulkUpdateUsers` 改管理员资格时拿的同一把锁），**拿到锁之后才读角色**，是管理员就只记录，不是才停用。否则"读到是普通成员 → 同时被提升 → 照样停用"会留下被停用的管理员。锁的顺序是先主体锁（`LockModerationSubject`）再管理员锁，`UpdateUser` 只拿管理员锁，拿着管理员锁的没有谁会去等主体锁，所以不会死锁。（若先处罚、后被提升，那是管理员对一个已停用账号做的提升，不算违反。）计数**从该主体上一次被处罚之后**算起，所以管理员启用账号后重新来过，不会下一条消息又触发。触发处罚的那个请求直接以处罚作答（`moderate` 里 `recordBlocked` 的结果）：403 `account_disabled` 带原因，页面随即换成停用页。
- **被拒绝的发送留在对话里**（发送、以及改写这条被拒绝的消息本身会留，见下一条；改写别的提问和回答被拒什么都不留，文字回各自的编辑框）：`CreateMessage` 里 `moderated` 返回「内容被拒」（`refused`，包括以处罚作答的那条）时，`keepRefused`（`moderation_kept.go`）在 `lockLive` 下的一个事务里于转录末尾写一行 `blocked` 的 user 消息（`parts` 只有文字），提交后发 `transcript_changed`（无 `from`，让别的标签页取最新一页），然后照旧以 422 `content_blocked` 作答，`details` 多一个 `messageId`（存下的那行）。不建 run，不认领附件（附件仍是输入框里没发出去的上传），`recordBlocked` 的计数和处罚不变；赚到处罚的那条（403 `account_disabled`）照样存，账号被重新启用后能看到。**对话里有 run 在写、或对话已被删时什么都不存**（行会落进正在写的回复中间；页面在 run 进行时也不让发），此时 422 没有 `messageId`；存不下来只记日志，不改变回答。
- **被拒绝的消息要先改写**（`requireRevised`，`moderation_kept.go`；错误 409 `revise_refused`）：对话的末行是 `blocked` 的消息时，发送（`CreateMessage`）、重新生成（`RegenerateAnswer`）、回答 `ask_user`（`AnswerQuestion`，被拒绝的行可以写在模型的提问之后，那个提问仍算「在等」，但不能越过它去回答）都被拒绝，否则模型会像是回答了它从没见过的话（用户发句「。」，转录读起来就是模型答了那条被拒的消息）。每处检查两次：进入时先问一次（不审核、不记 strike、不写任何东西，省一次审核调用），事务里 `lockLive` 之后再问一次（和别的起 run 的检查同一把锁，`GetLastMessage` 取末行，所以与改写它的请求、与另一条被拒绝的发送竞争时转录仍一致）。出路有两条：①改写这条被拒绝的消息（`POST .../messages/{id}/edit`）；②改写更早的某条提问，它把被拒绝的行连同之后的一切删掉（照旧允许）。改写被拒绝的消息时：`attachmentIds` 只对被拒绝的消息有效（它自己没有文件，输入框里没发出去的上传随新措辞一起认领；别的消息带它是 400 `attachments_not_editable`，别的消息保留自己的文件），新措辞连同这些图片一起重新审核（和发送一样读一次图并记摘要，`checkedImages`）；通过：被拒绝的行删掉、新提问写在末尾、建 run，和任何改写一样（带 `transcript_changed` 的 `from`）；**再次被拒绝：新措辞替换旧的被拒绝行**（`keepRefusedEdit`，`storeRefused` 的 `replaced`）——同一个事务里在 `lockLive` 下确认旧行**仍是末行**、没有 run 在写，才删旧行写新行（`DeleteTranscriptFrom` 只删它自己），422 的 `details.messageId` 是新行，别的标签页收到 `transcript_changed` 的 `from` = 旧行；旧行不再是末行（旧数据里它后面有行）、有 run 在写、对话已删时什么都不变（删它会连后面的一起删），照旧 422（没有 `messageId`）。所以转录里永远最多一条「当前」的被拒绝行：`storeRefused` 在末行已是被拒绝的消息时也不再追加第二条（两条发送同时被拒，只留先到的，后到的只得 422 没有 `messageId`）。每次被拒绝的尝试照旧记 strike（改写和发送一样）。新增会往转录末尾写行、起 run 的路径，都要过 `requireRevised`。
- 被拦的提示：`content_blocked` 的 `details` 里，处罚可能随后到来时（设了次数、不是管理员）还有 `strikesLeft`（窗口内再几次就处罚）和 `windowHours`。前端 `useSendError`：弹出「未通过内容审核」的提示，不带错误编号（这不是故障），有 `strikesLeft` 时附一句「N 小时内再违规 M 次，账号将被停用」。**被拒绝的消息本身是转录里的一行**，`buildTurns`（`chat-core/src/transcript.ts`）把 `blocked` 的 user 行画成用户气泡，后面紧跟一个 `refusal` turn，由 `RefusedReply` 画成模型样式的回复，正文 `RefusalCard`：一行工具活动样式的状态行「内容违规 · 未发送」、正文「请修改提示词后再试」，不加框；刷新后、别的标签页和设备上都一样。**剩余次数那一行只在收到 422 的页面里有**：`useSendMessage` 的 hook 级 `onError` 把响应里的警告按 `messageId` 记进 chat store 的 `refusals`，把这一行先塞进缓存的消息列表（`appendRow`，免得气泡撤掉到行出现之间闪一下）再 `refreshNewestMessages` 取回服务端的版本，不要 `invalidateQueries` 消息键；刷新之后卡片没有这一行。`isRefusedTurn` / `sentTurns` 把被拒绝的行和它们的卡片排除在「问过、答过的对话」之外：重新生成按钮挂在最后一条回答上（最后一条提问是最后一条没被拒绝的）、`pendingQuestion`（后面的被拒绝消息不让模型的提问消失，也不算回答它）、搜索预览都用 `sentTurns`；`buildTurns` 里被拒绝的行**不**结束前面的回复块（`ask_user` 的回答续写写在它后面，仍属于提问的那一块）。输入框的文字和文件原样留着，拒绝后仍在输入框里（`handleSend` 的 `onError`）；此后输入框就是这条消息的编辑器（见下「输入框就是被拒绝消息的编辑器」）。新对话的第一条消息被拒时，对话里已经有那一行，**不删对话、不回新对话页**，留在这个对话里、文字**和文件**还在输入框（`ChatView` 的 `handleSend`：只有没写任何东西的拒绝，如 `too_many_runs`、`no_models`，才删掉刚建的对话并回到空白页——`startWroteNothing`，`chat-core/src/start-failure.ts`，见「前端约定」里的「一个聊天页」）。**文件不会丢**：新对话流程里文件从头到尾没有离开过输入框（没有交接给别的页面，因为没有别的页面）；发送被接受（run 开始）才 `attachments.clear()`。上传了没认领的文件 24 小时内有效；服务器说 `attachment_unavailable`（文件不可用）时把这些文件从输入框去掉，免得再被拒一次（`returnableFiles`）。

## 自己写下的文字（自定义指令和记忆）

用户写的自定义指令和手写的记忆不是消息，但会被原样抄进每个对话的系统提示词（快照），所以同样要审，否则发一句 "hello" 就能把违规文字带给模型。检查在两处，代码在 `internal/api/moderation_text.go`，调的还是同一个 `moderate`：

- **保存时**：`UpdatePersonalization`（只审**改了**的字段，原样传回的不重审）、`CreateMemory`、`UpdateMemory`（审 `memory.Clean` 之后的文字）。不通过是同样的 422 `content_blocked`（`details` 同发送，没有 `messageId`）、计 strike、够了就处罚，**什么都不保存**（含同一请求里的开关）；检查不了且设了「拦」是 503 `moderation_unavailable`。来源 `instructions` / `memory`。
- **取快照时**：对话第一次起 run 前，快照里**没审核过**的文字（保存时审核是关的、或后来才开的审核）一次批量审核（`snapshotVet`，拼成一段带标签的文字，一次 `moderate`）；批量不通过才逐条再查，找出是哪几条，其余照常进快照。不通过的**不进快照**（对话照常继续，快照之后字节不变），记 `moderation_events`，来源 `snapshot`。**这类事件不算 strike**（`CountUserStrikes` 排除 `snapshot`）：文字是以前写的、此刻并没有发出什么，不该因为一句 "hello" 把账号停了；同样的字发成消息仍然算。检查不了时按 `moderation_on_error`：拦 → 这次发送/改写/重新生成/回答以 503 `moderation_unavailable` 拒绝（此时什么都没写，没有快照）；放行 → 文字进快照，但不记为审核过，下个对话再问。
- **「审核过」怎么记**：对每个指令字段和每条记忆存**通过审核的那段文字的 SHA-256**（`users.instructions_{about,style}_checked_hash`、`user_memories.checked_hash`，`memory.Hash`）；改一个字，哈希就对不上，自动回到「没审核过」，没有标志位要清。快照时被拒的另存 `…_blocked_hash`，所以被拒过的字不会每个新对话再问一遍（也就不会每次再记一条日志），改了才重新审。**只有真的审过才记**：审核关着、管理员被豁免、服务出错而放行都不记（`checkText` 用 `moderationTrace`——`moderationFailed` 里的一行——分辨「通过」和「没法检查所以放行」，并在检查前后各确认一次审核确实开着）。
- **模型写的记忆不审**（模型输出，来自已审核的对话）：它们写入时就记为审核过（`By.vouched`）；用户改了其中一条就成了用户的文字，按用户的算。**判断「审核过」只看哈希，从不看 `source`**：用户改写模型写的记忆，`source` 仍是 `model`，但 `UpdateMemoryContent` 总是用调用方给的哈希换掉旧的（用户的改写没审过就是 NULL），所以这条记忆在下个快照会被审。迁移 `…_moderated_instructions_and_memories.sql` 当初把所有非 `user` 来源的记忆回填成审核过，这对「v1.0.0 之前被用户改写过的模型记忆」是错的（那时改写不改 `source`）；已发布的迁移不能改，`…_unearned_memory_checks.sql` 把所有非 `user` 来源记忆的 `checked_hash` 清掉（回填的记号和之后赚到的记号都是当前文字的哈希，分不开，所以保守地全清；代价是每人下一个快照多一次批量审核，审核关着时没有代价；`blocked_hash` 和 `user` 来源的记号不动，自定义指令当初没回填，也不动），之后模型新写的照旧在写入时记为审核过。撤销（`Undo`）恢复的旧文字不带哈希，开着审核时下个快照会审一次。
- 已有快照的对话不重审、不重取：快照是这个对话的，改了指令或记忆只影响之后的新对话。

## 用户标识（上游请求里的 end-user id）

- 每个发往模型的请求带 `llm.Request.User`：`HMAC-SHA256(密钥, 用户 id)`，十六进制取前 32 位。密钥 `end_user_key` 在 `app_settings`，首次使用时生成（`InsertSettingIfMissing`，和 `storage_signing_key` 一路），**没有任何接口读或写它**；不含邮箱，别人拿不到密钥就反推不出 id。
- 线上字段：OpenAI Chat Completions 和 Responses 是 `safety_identifier`，Anthropic 是 `metadata.user_id`，Gemini 没有这个字段所以不发。这几个键在 `Options.Extra` 里是保留键。
- 第三方兼容端点可能拒绝不认识的字段，所以每个渠道有开关「发送用户标识」（`channels.send_user_id`，渠道表单里可改）：新建时 base URL（空则取该渠道类型的默认地址）的主机是 `api.openai.com` / `api.anthropic.com` 就默认开，否则关；迁移按同样规则给已有渠道回填。适配器只在开关开着且请求带标识时才发（`Config.SendUser`）。
- 传到哪：run 的每次请求（`Options.EndUser`）、标题（含按需标题）、上下文压缩（只在 run 内）、模型审核的请求。新写会用模型的路径也要带上 `User`。

## 前端

- 被拒绝的发送 / 改写 / 回答走已有的发送错误路径（`useSendError`）：提示「这条消息未通过内容审核，没有发送」，**不显示类别**；输入框的文字和文件原样留着（`handleSend` 的 `onError`），改写的输入框在被拒绝后带着打的字重新打开（`ChatView` 的 `refusedEdit` → `UserMessage.restoredDraft`，因为改写期间那条消息被藏起来了，本地 state 保不住）。
- **输入框就是被拒绝消息的编辑器**：对话的末行是被拒绝的消息时（`composerMode(turns)`，`chat-core/src/revise.ts`，纯函数有 vitest；判定来自 `buildTurns` 给末尾那张拒绝卡片标的 `last`，`refusedTail`：后面还有行的旧数据不算，运行中、改写进行中那条消息被藏起来也不算），①输入框上方一行安静的小字「修改被拦下的消息后重新发送」（`Composer` 的 `note`，`.n-composer-note`，和活动状态行一样的灰色小字，不是红框）；②从输入框发送是**改写那条消息**（`useEditMessage`，带输入框里的文件的 `attachmentIds`），不是新消息；③输入框为空时（刷新、换设备、另一个标签页）用被拒绝的原文填上（`reviseDraft`，对每条被拒绝的消息只填一次，`filledFor`，所以用户清空后不会又被填回；本页刚被拒绝时输入框里已经有字，不动）；④再次被拒绝：`useEditMessage` 的 `onError` 里 `refusalOf(error).messageId` 有值就 `forget({from: 旧行})` 再 `keepRefused`（和被拒绝的发送同一条显示路径，缓存里旧行换成新行，警告按新行的 id 记），输入框仍有字、仍在改写模式；⑤通过：被拒绝的行和卡片消失、新提问和回答在位，和任何改写一样；⑥不再提供别的路：`regenerable(turns)`（取代 `ChatView` 里内联的 `last`）在末行被拒绝时为 null，所以重新生成按钮不显示（`onCompress` 同理）；`pendingQuestion` 在这时为 null，所以 `AskUserDock` 不显示；被拒绝的那条用户气泡不显示改写小笔（输入框就是编辑器，别处的旧被拒绝行和别的提问仍可就地改写）。页面不知道对话已停在被拒绝的消息上时（另一个标签页、另一台设备造成的）发送得到 409 `revise_refused`：`useSendError` 弹提示并 `refreshNewestMessages`，输入框随即变成编辑器。
- 保存自定义指令 / 记忆被拒：设置对话框的个性化页签和记忆管理器都**就地**说出来（`useSaveRefusalText`，`chat-core/src/moderation-refusal.ts` 的 `saveRefusalOf` 有 vitest）：「这段文字未通过内容审核，没有保存」，有 `strikesLeft` 时附同一句警告；503 `moderation_unavailable` 说「审核暂时不可用，没有保存」。输入框 / 草稿里的字原样留着，一改字就清掉提示；个性化页的提示在字段下面，记忆管理器沿用它自己的错误行。管理后台日志的「来源」列把这些值都显示出来（`instructions`、`memory`、`snapshot`、`task`、`task_run`、`document` 是发送、改写、回答之外的来源）。
- 后台：系统 →「审核」页签（`features/admin/moderation/`：zod 模式 + vitest、表单），「审核日志」页（`features/admin/moderation-logs/`，`DataTableCursorPagination`，账号行链到用户页），渠道表单的「发送用户标识」开关。使用日志的类型过滤里有「内容审核」。
