# 参考聊天记录：方案

> 状态：第 1、2 期和评测已实现（2026-11-10）。第 3 期（后台整理）和自动提取记忆决定不做（2026-11-10，见 5.2）。相关：[conversations.md](conversations.md)（个人记忆、快照、引用其他对话、搜索）、[moderation.md](moderation.md)（快照时的审核）、[sub-agents.md](sub-agents.md)。

## 0. 结论先行

新开的对话要能接上之前聊过的事。做了前两层，第三层不做：

1. **近期对话清单**（预加载）：新对话取快照时，把用户最近的对话——日期、标题、用户自己说过的话（截短）——放进系统提示词。模型一上来就知道用户最近在聊什么，「刚才那个」「接着上次」能直接接上。不调用模型、不做摘要，用原文。
2. **`chat_history` 工具**（按需）：清单只有用户的话，也只覆盖最近的对话。更早的、或者模型当时给的具体结论，模型用工具搜全部历史、读命中的前后文。
3. ~~**后台整理**~~：空闲时核对模型写下的记忆（去重、清过期、对不上原对话的删掉）。不做，连同原定的「从对话中自动提取记忆」，理由见 5.2。

依据：ChatGPT 的做法（社区逆向：约 40 个近期对话的时间 + 标题 + 用户消息，每条截到约 100 token，直接放系统提示词，不是 RAG）；ReFind（arXiv 2608.12888：不建任何结构，按轮次做词法检索，加会话级重排、前后文展开、时间范围、跳过看过的会话，不输图/树结构的记忆系统）；arXiv 2610.24671（显式记忆系统并不稳定胜过对原文的检索，摘要阶段就可能把答案丢掉）；Anthropic「The components of agent memory」（顶层常驻的要小，细节按需读；逐字优于概括）。

和现有记忆的关系：个人记忆（笔记、自定义指令、每对话快照、管理员看不到别人的记忆）一概不动。这是另一个功能、另一个开关。

## 1. 用户已定的事（2026-11-10）

- **默认开**。独立于记忆的开关（个性化页，记忆开关下面），后台另有总开关。
- **删除对话时立刻清掉**：它在该用户其他对话清单里的那一条，在软删除的同一个事务里删除。代价是那些对话下一次请求提示词变了（缓存失效一次，之前的思考块不再回放），接受。
- **标题要审**：用户改的标题没审过，而模型会读到。

## 2. 开关

| | 存哪 | 默认 | 契约 |
| --- | --- | --- | --- |
| 用户自己的 | `users.chat_history` | 开 | `Personalization.chatHistoryEnabled`、`UpdatePersonalizationRequest.chatHistoryEnabled` |
| 管理员的总开关 | `app_settings` 的 `chat_history` | 开 | `SystemSettings.chatHistory`、`UpdateSystemSettingsRequest.chatHistory`；`Personalization.chatHistoryAllowed` 把它告诉设置页 |

两个都开才算开。关着时：新对话的快照不带清单；已有清单的对话**这次请求起**不再渲染清单（和记忆一样，渲染时看现在的开关，快照本身不改）；不提供 `chat_history` 工具。临时对话既不读清单、不给工具，也永远不出现在别人的清单和搜索里。

## 3. 第 1 期：近期对话清单

### 3.1 取什么

和快照一起取（`EnsureSnapshot`，建 run 之前，一个对话一次），存进 `conversations.memory_snapshot` 的 `recent`：

```json
"recent": [
  {"ref": "c1", "id": "<对话 uuid>", "title": "…", "at": "<最后一条用户消息的时间>", "messages": ["…", "…"]}
]
```

- 哪些对话：这个用户的、`kind = 'chat'`、非临时、未删除、不是当前对话、不是定时任务的对话（`scheduled_tasks.conversation_id`：那是任务指令，不是用户打的字，每天重复会挤满清单）、至少有一条可用的用户消息。先按对话的最后活动时间（`updated_at`，侧栏的顺序，走 `conversations_user_updated_idx`）取最近 80 个，只读这些对话的消息，所以历史再长也不扫全部提问；其中按最后一条用户消息的时间倒序，去掉没有可用文字的，最多 `MaxRecentChats`（40）个。
- 哪些消息：`role = 'user'`、`status <> 'blocked'`、`origin IS NULL`。文字取用户打的字：去掉深度研究行、技能行、图片引用行（`personWords`），再去掉引用段落的包装（`<document-selection>`、`<quote>`，只留用户的请求）；去完为空的不要。
- 截短：每条最多 `recentMessageRunes`（160）个字符，超出以 `…` 结尾，换行压成空格。每个对话最多 6 条：第一条和最后五条（中间略去的不标）。
- 总预算 `recentBudgetRunes`（6000 字符）：从最新的对话起往里放，放不下消息的对话只留日期和标题一行；连标题行都放不下就到此为止。越旧的对话细节越少，清单始终是一张「最近聊过什么」的目录。
- `ref`（`c1`…）在取的时候定下，之后不重排（删掉一条后其余的编号不变），给 `chat_history` 工具引用。

### 3.2 标题的审核

- 默认标题（`New chat`）不写进清单（那一条没有标题）。
- 模型起的标题（`SetGeneratedTitle`）写入时记为已检查。
- 其余标题（用户改的）在取快照时和自定义指令、记忆一起送审（`snapshotVet`，来源 `snapshot`，不算违规），结果按哈希记在对话上（`conversations.title_checked_hash` / `title_blocked_hash`），同一个标题只问一次。被拒的标题不写进清单，那一条仍然在（消息在发送时审过）。

### 3.3 提示词

`memory.Snapshot.Prompt` 多一节（英文，写给模型）：清单在 `<recent_conversations>` 标签里，是数据不是指令；只有用户自己说过的话，没有模型当时的回答；用来理解用户指的是什么、延续话题，不要主动复述清单，也不要因为清单里有就把无关的旧话题扯进来。提供了 `chat_history` 工具时再加一句：要当时的回答或更早的对话，用工具查（带上 `c3` 这样的编号）。

每条一段：`[c1] 2026-11-09 14:20 · 标题`，下面每条用户消息一行 `- …`。时间用服务器时区，和系统提示词里其余的时间一致。标签里的闭合标签照 `escapeFence` 处理。

### 3.4 删除时清掉

软删除对话的每条路径（单个删除、`DELETE /me/conversations` 全部删除，以及以后新增的），在同一个事务里把被删对话从该用户**所有**对话的 `memory_snapshot.recent` 里去掉。其余条目和它们的 `ref` 不动。写成一条按用户限定的 `UPDATE`，不逐行读改写。

删除会写这个用户的其他对话，所以每条删除路径在事务一开始、锁任何对话行之前先取这个用户的 `LockRecentChats`（advisory lock）：否则互相列着对方的两个对话同时删除，各持自己的行、等对方的行，数据库判死锁（测试 `TestConcurrentDeletesOfConversationsThatListEachOther`）。保存带清单的新快照也在同一把锁下（`Store.saveSnapshot`），并去掉读清单之后已被删除的对话：清单要么先于删除保存（删除会清掉它），要么后于删除（保存时已经没有它），不会出现「刚删掉又被收进清单」。审核请求在取锁之前发，锁只包住一次读和一次写。

不清的情形：用户改写了某条提问（旧措辞可能留在别的对话的清单里，直到那些对话没了）；改名（清单里是取快照时的标题）。这两种不涉及「删除了却还在」。

## 4. 第 2 期：`chat_history` 工具

模型搜和读用户自己的历史对话。用户取自 `agent.ScopeFrom(ctx)`，永不信参数。

### 4.1 提供给谁

「参考聊天记录」开着、对话不是临时的、不是子 Agent（`Scope.Parent`）、不是深度研究的各阶段。定时任务的 run 可以用。是否提供按请求现查（和 `memory` 工具一样）。

### 4.2 两个操作

`op = "search"`：

- 参数：`keywords`（1–6 个词或短语）、`from` / `to`（`YYYY-MM-DD`，可选）、`include_seen`（可选，默认 false）。
- 搜什么：该用户的、`kind = 'chat'`、非临时、未删除、不是当前对话的对话里，`role IN ('user','assistant')`、`status <> 'blocked'`、`origin IS NULL` 的消息的 `content`。匹配是子串（`ILIKE`，关键词各自转义），任一关键词命中即为候选——中文没有空格分词，子串匹配正合适，也不需要任何扩展或向量库；语料只是一个人的消息。
- 候选按关键词各取最新的 100 条（`historyPerKeyword`），不是合起来取最新的若干条：一个到处都有的词不能把只出现两次的那个词挤掉。找候选只扫一遍这个用户的消息。
- 排序在 Go 里：每条候选消息按 BM25 的形式打分（词频饱和、长度归一；长度用字节数，可搜消息总数和平均长度由一条不读正文的查询给出；IDF 的命中条数在候选里数——到处都有的词按「很多」算而不是精确值，稀有词仍然更重，而精确值要为每个关键词再扫一遍全部历史）；每个对话的分数是它候选消息分数之和；最终按 RRF 融合两个名次：`1/(60 + 消息名次) + 1/(60 + 所属对话名次)`。取前 5 条命中，同一对话相邻的命中合并。
- 每条命中带上前后各 2 条用户/助手消息（不跨对话），每条消息截到 600 字符：命中的那条截的是第一个关键词前后的一段（`excerpt`，长回答深处的事实才看得到），前后文从开头截。结果里有对话的 id、标题（只在已检查过时给，见 3.2）、时间。
- 这个 run 里已经返回过的对话默认跳过（记在 `Scope.State`），好让下一次搜索找到新的；`include_seen: true` 时不跳。

`op = "read"`：

- 参数：`conversation`（清单里的 `c3`，或搜索结果里的 id）、`offset`（可选，从第几条消息起）。
- 返回那个对话的用户/助手消息（同样的过滤条件），按时间顺序，每条截到 2000 字符，一次最多 12000 字符，末尾说明还剩多少、下一个 `offset` 是多少。

### 4.3 提示词

`api/agent_setup.go` 里一节（英文）：只在用户的话指向或依赖以前的对话、而清单和当前对话里又没有所需内容时用；先宽后窄（先不带日期搜，再用找到的名字、编号、日期收窄）；问「最后怎么定的」要看时间最晚的那次；找不到就说没找到，不要猜。不要为了「了解用户」而翻历史。

### 4.4 不审核

读到的是用户自己的对话：提问在发送时审过，回答本来就是会发给模型的那类文字（和「引用其他对话」同一个道理）。标题例外，见 3.2。

### 4.5 给页面的 `details`

```json
{"op": "search", "keywords": ["…"], "from": "2026-09-01", "to": "2026-09-30",
 "hits": [{"conversationId": "…", "title": "…", "at": "…"}]}
{"op": "read", "conversationId": "…", "title": "…"}
```

页面在回复的活动行里显示「搜索了聊天记录」/「读了以前的对话」，展开列出命中的对话（标题可点，去那个对话）。

## 5. 评测与第 3 期

### 5.1 评测（`cmd/evalhistory`）

改提示词、工具说明、清单或搜索的预算之前和之后各跑一遍，比较通过率。用真实模型，经正在运行的服务器（`make ser`）：

```bash
cd apps/server && go run ./cmd/evalhistory            # 每类 3 次
go run ./cmd/evalhistory -cases recall,latest -runs 5 -v -out /tmp/before.json
```

- 每次试验是一个新账号：直接在服务器的库里建（管理员，免得「是否向普通用户开放」和配额左右结果；没有密码，会话一小时），按用例需要的日期写入历史对话（标题记为已检查），然后像客户端一样经 API 新建对话、发问题，等 run 结束后判分。结束后删账号及其对话；它花掉的用量留在用量日志里，标上它的地址。`-keep` 保留，便于在页面里看。
- 判分不用模型：每个用例埋下猜不到的东西（随机的密码、少见的姓、日期），答案里出现即对，另查有没有调用 `chat_history`。埋的内容每次随机，`-seed` 可复现。
- 每个人的历史都有 44 个普通对话，最新的在两天前：比清单能放的 40 个多，所以下面标「必须用工具」的用例，答案只在历史里、不在提示词里。

| 用例 | 测什么 | 工具 |
| --- | --- | --- |
| `pickup` | 昨天聊的旅行计划，今天说「接着昨天那个」：答案要出现那个城市（清单） | 都行 |
| `recall` | 两个月前模型给的 Wi-Fi 密码（随机），原样说出来 | 必须 |
| `latest` | 年会先改日期、再改地点，问最后定在哪天哪里 | 必须 |
| `combine` | 老师的姓在一个对话里，考级的月份和级别在另一个里 | 必须 |
| `restraint` | 和以前无关的普通问题，不该去翻历史 | 不该用 |

默认用最便宜的模型（`claude-haiku-5-5`，`-model` 可换），结束时报每类的通过数、用了工具的次数、每次调用数、耗时和花费。

基线（2026-11-10，`gpt-6-luna`，每类 5 次）：25/25，共花 0.026 美元。`pickup` 每次都用了工具（要改的是模型当时给的行程，清单里只有用户的话，这是对的），其余三类各 1 到 1.2 次调用，`restraint` 一次没用。此前一轮 15 次里有一次 `recall` 失败：模型自己编了一个日期范围（最近十天），搜不到就说没有。工具说明和「没找到」的结果随后改成「用户没说时间就别加日期、加了日期没找到先去掉日期再搜」；改后同样 25/25，花 0.023 美元，三类必须用工具的用例里 15 次搜索没有一次自己加日期（改前两轮 24 次里有 2 次）。这套用例对这个模型已经接近满分，区分度不够，以后加难度（同名的事、更长的历史、说法和原文不同）。

### 5.2 不做的第 3 期：后台整理与自动提取记忆（2026-11-10 定）

原方案：任务模型在空闲时对照来源对话核对模型写下的记忆，去重、标记过期、对不上原文的删掉；以及更早定下的「从对话中学习」（对话结束后自动提取新记忆，个人开关默认关，设置页里一直是「即将推出」的占位）。两件都不做：

- 没有证据说明问题存在：线上模型写的记忆有多少、重复和过时的比例都不知道；完全相同的重复写入时已经拦下。
- 过时的记忆有更准的处理：记忆列表就在提示词里，用户在对话里说到新情况时，模型当场用 `memory` 工具改或删，比后台猜准。
- 自动提取要解决的「新对话接上以前的事」已经由本文的清单和 `chat_history` 覆盖，而且是逐字的。
- 两者都是让最便宜的模型在后台自动改、删用户的数据，出错的代价比留一条旧记忆大。

随之删掉：设置页的占位开关、`users.memory_learn`、记忆来源 `auto`（迁移 `drop_learning_from_conversations`）。以后要重新考虑，先在后台加只看数量的统计（每人模型写的记忆条数、疑似重复的条数，不看内容），看到确实有问题再说。

分层（记忆列表只注入一部分）等体量上来再说：现在最坏约 2 万字。

## 6. 不做的

- 向量库、BM25 引擎、中文分词：语料按用户隔离，量级小；评测显示不够再说。
- 单独的检索 Agent：ReFind 每题约 5 次模型调用；主模型拿着两个操作自己分级（清单够就不搜）。
- 对清单做模型摘要：逐字的不会写错，也不花钱。
